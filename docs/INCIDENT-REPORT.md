# Incident report: live DDoS against the VPS (October 2026)

Two kinds of evidence exist in this repo and they are kept apart on purpose:

| Kind | Where | What it shows |
|---|---|---|
| **Live incident** | this document, `docs/evidence/` | A real attack on the real VPS, observed on OVH's dashboard and on the host |
| **Synthetic test** | `docs/test-logs/ftest-v8.log` | The filter's drop decisions at 555k-703k pps, replayed through `BPF_PROG_TEST_RUN` |

The live attack was real. It was not generated by this project. The 555k-703k pps
figures are **not** from the live attack; they come from the synthetic test.

## Summary
A commercial stresser hosted inside OVH (AS16276) was used against the VPS's public
IPv4 address. OVH's Anti-DDoS dashboard classified the traffic as `OTHER`, `TCP_NULL`
and `UDP` on the /32. The owner reported roughly 200 Mbit/s and 200,000 packets per
second, and that the service went down. OVH showed mitigation active while ~285,000
pps was still being accepted. The host-side filter was then built, measured and
iterated in real time while the attack was running.

## Environment
- OVH VPS, 2 vCPU, virtio_net (1 queue), Ubuntu, Tailscale exit node.
- Public IPv4 on `ens3`. XDP in generic mode only (native not available).
- Host layers: XDP/eBPF pre-filter, nftables `inet ovh_fortress`, conntrack.
- Provider layers: OVH VAC and Edge Network Firewall.
- Monitoring: `monitor/clueless.py` (terminal dashboard over SSH) and `xdp-stats`.

## Key finding: the attacker was inside OVH
OVH's Edge Network Firewall documentation says it handles traffic coming from outside
the OVHcloud network. The attacker's source addresses belonged to OVH's own ASN, so
the edge firewall could not be relied on and the host layers carried the defence.

## Timeline
| Step | Observation | Action |
|---|---|---|
| 1 | Dashboard showed XDP dropping (2,134 dropped) with ~134k pps inbound, but the owner reported the service still being hit | Found the dashboard's "coming through" figure counted packets XDP *passed*, not packets that reached the host. Relabelled it. |
| 2 | Flood of TCP ACK packets (1268-byte) to port 51820 passing; `wg-flood-block` counter reached 12,431 packets | Inserted an explicit drop for tcp/udp 51820. Root cause: `nf_conntrack_tcp_loose=1` let mid-stream ACKs create state. Set it to 0. |
| 3 | OVH dashboard: `OTHER`, `TCP_NULL`, `UDP`; service reported down; ~200k pps, ~285k pps accepted despite mitigation | Wrote XDP v7, then v8: NULL-flag drops, per-source and shared UDP buckets, ACK/SYN rate limits, class valves, global ceiling |
| 4 | v7 broke DHCP (private-source bogon rule) | Moved the DHCP check ahead of the bogon check |
| 5 | v8 first pass dropped 58% of legitimate upload ACKs at baseline | Raised ACK limit to 8000/s, burst 16000 |
| 6 | Dropping all bare SYNs would blind the port 1337 tripwire | Replaced with a 500/s shared sample valve |
| 7 | v8 deployed and confirmed attached (`xdpgeneric`), counters read through `xdp-stats` | Persisted via systemd and nftables drop-ins; verified after cold reboot |

## What changed as a result
- XDP v8 (`xdp/fortress_xdp.c`), loaded with a timed rollback so a bad filter cannot lock out SSH.
- `zz-wgblock.nft`, `zz-bait.nft` (port 1337 tripwire), `zz-tsexit.nft`.
- `nf_conntrack_tcp_loose=0`.
- Dashboard fix so it separates "dropped by XDP", "dropped by nftables" and "passed".
- OVH Edge Network Firewall rules reduced to an allow-list (see `DEPLOY.md`).

## Limits
- Live pps and Mbit/s figures are from dashboards and the owner's reading, not from
  a packet capture on the host.
- XDP in generic mode adds cost the replay test does not include.
- A single VPS cannot absorb terabit floods; volumetric protection is the provider's.
- Nothing here includes the attacker's identity, addresses or any report to a third party.
